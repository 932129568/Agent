## 1. P0 修复：群聊消息截断丢失

### 1.1 缺陷回顾（R97 §7.1 / R98 §8-B 记的那条）

四处截断动作会缩短 `s.messages`，但都不推进 `s.updatedAt`：

| 入口 | 文件:行（改前） | 行为 |
|---|---|---|
| `regenerate` | `frontend/src/chat/send.js:262` | 截掉最后一次用户消息之后的内容 |
| `msgRecall` | `frontend/src/components/markdown.js:293` | 撤回一条及其后续 |
| `msgEditResend` | `frontend/src/components/markdown.js:369` | 编辑后重发，截断其后 |
| `msgRollback` | `frontend/src/components/markdown.js:393` | 切片移入 `__rollbackBuf.msgs` |

合并侧 `frontend/src/sessions/store.js:148-157` 原逻辑：

```js
if (!prev || (s.updatedAt || 0) > (prev.updatedAt || 0)) byId.set(s.id, s);
put(backend); put(local);   // 同 updatedAt 时取后端
```

时间戳没变 ⇒ 平局 ⇒ 取后端 ⇒ 后端那份是截断前的长版本 ⇒ **截断失效**；反过来若后端恰好是截断版、本地是完整版，则**完整历史被覆盖**。

### 1.2 修复（两个动作，缺一不可）

**动作一：四处截断后推进时间戳**

```js
s.messages.splice(...);
s.updatedAt = Date.now();   // R99 P0
```

最终行号（改后重新 grep，已漂移）：`send.js:267`、`markdown.js:294`、`markdown.js:371`、`markdown.js:398`。

**动作二：合并平局加二级判据**

```js
if (!prev) { byId.set(s.id, s); return; }
const cur = s.updatedAt || 0;
const old = prev.updatedAt || 0;
if (cur !== old) { if (cur > old) byId.set(s.id, s); return; }
// 平局：消息条数多的一侧胜；条数也相等时仍取后端（旧语义）
if ((s.messages || []).length > (prev.messages || []).length) byId.set(s.id, s);
```

**严格比较分支零放宽**：`cur > old` 入、`cur < old` 不入，与原文等价。唯一行为变化是「时间戳相等且新到的一侧更长」时由「不入」变为「入」。

### 1.3 为什么这个修法不会引入另一种数据丢失（三条论证）

1. **「平局取后端」的原始理由被保留**。本地镜像是配额投影（最近 24 会话 + 正文 2k），投影**不改变消息条数**。所以「投影版 vs 后端完整版」在合并时条数必然相等 ⇒ 新判据不触发 ⇒ 仍取后端。这条有专门用例守着（`test_tie_with_equal_length_still_prefers_backend_projection_guard`，断言合并后正文长度 == 3000 而非 2009）。
2. **条数判据只在「时间戳相等 + 条数不同」这个窄缝生效**，而该状态在正常路径不可达：任何真实截断现在都会 bump，任何真实追加/编辑本来就会 bump，正常双写后两侧时间戳与条数同时相等。能落进窄缝的只有「某一侧落盘失败的残影」，此时条数多的一侧严格包含另一侧信息。
3. **反向风险已被显式测住**。截断后 bump 会让截断版比后端「新」，这正是用户意图（他要删掉那些消息）。代价见 §6-1。

### 1.4 回归用例 `tests/test_r99_truncation_merge.py`（8 条，零新依赖）

真实源码（`store.js` / `markdown.js` / `send.js`）在 Node VM 里跑，只 stub 浏览器环境（DOM / localStorage / pywebview 桥）。

**改前 6 failed / 2 passed，改后 8 passed**（原始输出见工程师与 QA 报告）。用例清单：

## 2. `--text-3` 对比度提档（B 方案）

### 2.1 改动（只有两个值）

```diff
- --text:#141413;--text-2:#5E5D59;--text-3:#6F6D66;   ← 亮档 :263
+ --text:#141413;--text-2:#5E5D59;--text-3:#67655E;
- --text:#F5F4ED;--text-2:#B8B5AA;--text-3:#969388;   ← 暗档 :309
+ --text:#F5F4ED;--text-2:#B8B5AA;--text-3:#A09D92;
```

`--text` / `--text-2` / `--muted` 未动；`--glass-blur` / `--glass-saturate` 未动；壁纸 `opacity .62/.65` 未动；样式文件数仍 14。

### 2.2 平底色对比度（标准 WCAG 公式，主理人与 QA 各自独立算出同值，4 位小数全中）

| 主题 | 底色 | `--text-2` | `--text-3` 旧 | `--text-3` 新 |
|---|---|---|---|---|
| 亮 | `#F0EEE6` | 5.6742 | **4.4578**（不达标） | **5.0218** |
| 暗 | `#141413` | 8.9782 | 5.9917 | **6.7877** |

亮档旧值本来就在 AA 线下方（4.4578 < 4.5），这次把它顶进线内；暗档本来就在线上，本次只加余量。

**顺带更正两处 R97 的旧错**（已写进 CSS 注释）：

- R97 记「次级色在理想底上只有 4.78:1」——标准公式算 `#6F6D66` on `#F0EEE6` 是 **4.4578**，4.78 对不上。
- R97 记暗档 `#B8B5AA` on `#141413` 有「9.03:1」——标准公式是 **8.9782**。连带「差 15 倍」也不成立（那是用错的 4.78 基线算的），按余量比是 `4.4782/0.5218 = 8.58`。

### 2.3 壁纸场景：**仍未达 4.5，且这是数学上限**

用 R97 记录的明档最差 3.61 反解最暗块的底色亮度：

```
L(#6F6D66) = 0.152761
L_bg_worst = 3.61 × (0.152761 + 0.05) − 0.05 = 0.681967
新 token：CR = (0.681967 + 0.05) / (L(#67655E) + 0.05) = 0.731967 / 0.179991 = 4.0667
```

**主理人反解得 4.07，QA 反解得 4.0667，两条独立路径吻合。** 但这仍是 **4.07 < 4.5**。

要达标，`--text-3` 的亮度必须 ≤ `(0.681967+0.05)/4.5 − 0.05 = 0.112659`。而 `--text-2`（`#5E5D59`）的亮度是 **0.1093**，已经低于该阈值 ⇒ **任何达标值都必然落在 `--text-2` 的 ±3% 亮度内，三级色阶坍成两级**。另一条路是把壁纸 opacity 从 `.62` 大幅下调（同一反解链给的是 `0.4x` 量级，等于放弃「透色上屏」）。

两条都是设计取舍，R99 的选择是：**两级不坍、opacity 不动，接受壁纸下次级文字偏弱**。要让壁纸下也达标，需另起一轮改 opacity 或调色板。

### 2.4 ⚠ 更重要的发现：R97 那套测量方法在本机已失效

QA 复测发现 R97 的 α-sweep **复现不出来**：本机当前壁纸（`TranscodedWallpaper` 3840×2160，2,785,156 B）是高对比照片，`L` 跨 0→1；在它上面 α=1 测得 ~1.00（R97 记 3.00）、α=.62 测得 ~1.30–1.39（R97 记 3.61）。

原因不是测量代码错，而是**指标退化**：满量程壁纸上总有一块 24×24 像素的亮度≈文字色，此时任何文字色的 CR 都趋近 1。**「最差块」在这种数据上恒等于最坏值，没有信息量，只能读分位。**

结论三条，写进 CSS 注释并在此重述：

1. R97 的壁纸最差值（明档 3.61、暗档 4.54）与那串 α-sweep **只对 R97 当期壁纸成立，不可迁移**。
2. 本机壁纸的「最差块」测量≈1.0–1.4 是退化值，**不能当作「R99 让可读性崩了」的证据**。
3. §2.3 的 4.07 是**算术反解**（锚在 R97 自己的基线壁纸上），**不是本机实测**。任何引用都必须带这个标注。

## 6. 未决项与边界

### 1. 🔴 壁纸下 `--text-3` 仍不达标（4.07 < 4.5）—— 待设计决策

两条路都已定量：① `--text-3` 压到 `L≤0.112659`（`#5E5D59` 的 L=0.1093 已低于此阈值⇒必然并档，三级坍两级）；② 壁纸 opacity 由 `.62` 大幅下调至 `0.4x` 量级（放弃透色上屏）。R99 取「都不做」。

### 2. 亮档三级色阶被压薄（可感知）

`--text-2` 5.6742 vs `--text-3` 5.0218，CR 间隙从 1.216 压到 **0.652**（压缩 46%）。数学上这是硬约束：任何 ≥4.5 的取值必然落进 `--text-2` 的 1.17 倍内。暗档间隙从 2.987 压到 2.191（压缩 27%）。

### 3. 图表调色板与 `--text-3` 已分叉

`--chart-4` / `--chart-axis` 在暗档仍是 `#969388`，而暗档 `--text-3` 已是 `#A09D92`。二者本是独立调色板，R99 未碰；**是否让图表轴跟 `--text-3` 走，需设计确认**。

### 4. 🔴 `compact-command.js:85` 同类缺陷未修

`archiveOldTasks()` 里 `s.messages.splice(0, end, {…归档占位…})` 把前 N 轮压成 1 条，**同样不 bump `updatedAt`**（该文件 `grep updatedAt` 零命中）。本轮故意没动：会多漂一个函数的定义体哈希，超出预期漂移面。建议并入下一轮。

### 5. 写入失败时本地投影版会被回写（既存风险，暴露面略增）

截断后若后端落盘失败、之后又有一次成功落盘，会把「本地镜像投影版」（正文被 2k 截断）写回后端。这是 W30「本地更新胜出」路径一直存在的风险，R99 让"截断"也走进该路径，暴露面变大一点点。替代方案（不 bump）代价是回退整个丢失，两害相权取轻。

### 6. `Date.now()` 同毫秒碰撞未处理

两次截断落在同一毫秒时 `updatedAt` 相等，会退回条数判据。人手点击间隔 >> 1ms，实际不可达，未加单调计数器。

### 7. `__rollbackBuf` 仍只在内存、不落盘；`groupFilesRead` 缺 `path` 时静默 return；PNA 响应头未加

前两条沿用 R98 的登记，第三条（`Access-Control-Allow-Private-Network`）仍只登记不实施。

### 8. 真机未复验

对比度、壁纸观感、会话列表置顶行为，全部是代码级 + canvas 测量 + VM 验证，**没有真机截图**。需用户装 `dist-electron-r98` 后目视确认，特别是亮档次级文字的观感。

## 7. 判据工程教训（本轮新增，接 R97 §四 24 条 + R98 §7）

1. **同一个数在两个地方写不一致，就是事故种子。** 本轮主理人给用户的阈值是 `L≤0.1127`，转给工程师时写成 `L≤0.1039`，工程师复算后拒绝执行并纠正。**任何跨消息传递的数字，发之前用同一条公式再算一遍。**
2. **测量指标会退化。** 「最差 24×24 块」在满量程数据上恒等于最坏值（总有块像素亮度≈文字色），此时它对颜色变化毫无分辨力。**用最差块之前先看被测量的数据分布；分布跨满量程时只能读分位。**
3. **改注释也要证明产物零变化。** 本轮用两条独立旁证：构建后 `harbor.html` 逐字节相同（CSS 被内联在产物里，相同即证明内联后的 CSS 相同）+ 压缩后 CSS 字节数不变（302,741 B）。**「我只改了注释」不是声明，是可验算的结论。**
4. **负控必须双向验收。** 「应红的翻红了」只证明判据能响，「应绿的仍绿」才证明它没误伤。QA 的 T1 两组四场景正是这个结构。
5. **变异测试要问「该红没红」，不是「红了就好」。** M6（`>` 改 `>=`）只翻 `projection_guard`，才说明那条守卫真的有分辨力。
6. **反解出来的数必须标成反解。** §2.3 的 4.07 锚在 R97 的基线壁纸上，不是本机实测。写成「实测通过」就是造假。
7. **区间/量级不要伪造精确值。** 壁纸 opacity 的达标阈值，因为 α-sweep 已声明不可迁移，只能给「0.4x 量级」而不能给「≤0.43」——同一条注释里给出精确阈值会与自己的前提矛盾。
8. **打包成功 ≠ 包是对的。** asar header 的 `integrity.hash` 是打包时读到的元数据，R91 就出现过声明与内容不一致。必须按 asar 格式回读字节自己算 hash（`qa/r90/verify-asar.mjs`）。
9. **注释里的数字会过期，而且没人会主动查。** 本轮修订前，`responsive.css` 里同时存在 `4.78`（旧错）、`9.03`（旧错）、`3.61`（旧值）三个数，且与同一注释块外的 `8.9782` 自相矛盾。**改 token 时必须 grep 全仓旧值，注释也算。**
