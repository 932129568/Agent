## 1. ① 群成员只输出纯文本、不写 `.md`

### 1.1 现象与用户的三种解释

用户在三个可能里选了第三种：**文件真的存在，但 UI 里看不到**。这个选择是对的，也把排查引向了正确的地方——而"看不到"本身又分两条完全不同的链：

- **群文件面板**（`#gbFiles`）读不到 → 本轮实测 **9/9 PASS，面板正常**，文件确实在 `C:\Users\陈\.glm-chat\group_files\<群 hash>\`（`s_1794924320958_cdt9x` → `g4826477444`，hash 已核）。
- **`.md` 根本不是模型用工具写的**，而是前端把成员正文归档出来的 → **这条才是真的**。

### 1.2 真根因：CORS 预检挡掉了自定义头

工具链本身是活的：`groupLoadTools()` 挂上了 22 个工具，`GROUP_LIMITS.memberToolRounds = 6`，模型确实返回了 `tool_calls`。断点在执行：

```
bridge.js:33-43   sid 存在时注入 x-harbor-sid / x-harbor-agent-loop；confirmed 时注入 x-harbor-confirmed
      ↓
server/src/routes/jsapi.js:48   读 x-harbor-sid
      ↓
server/src/app.js:37（改前）    Access-Control-Allow-Headers: 'content-type'     ← 只允许这一个
      ↓
electron/main.js:251            CORS_ORIGIN='null,harbor://app' → CORS 钩子生效
      ↓
浏览器预检拒绝 → Failed to fetch → executeTool 恒失败
      ↓
group.js:1447 熔断器注入「不要反复重试工具，请直接在正文里产出方案」
      ↓
成员输出纯文本 → 前端 groupArchiveHandoff() 归档成 .md
```

**一个缺陷同时解释两个症状**：用户看到"成员不写文件"（工具死了），又看到"有个 .md 但我不知道从哪来的"（归档产物）。

### 1.3 修复

`server/src/app.js:37`：

```js
// 改前
reply.header('Access-Control-Allow-Headers', 'content-type')
// 改后（固定白名单，不回显 Access-Control-Request-Headers——回显等于放开任意头）
reply.header('Access-Control-Allow-Headers',
  'content-type, x-harbor-sid, x-harbor-agent-loop, x-harbor-confirmed')
```

**为什么是固定白名单而不是回显 `Access-Control-Request-Headers`**：回显等于把"允许什么头"的决定权交给请求方，与本仓"绝不输出 `*`"同一精神。白名单与 `bridge.js` 实际发送的头一一对应，多一个少一个都由 S1 断言把住。

### 1.4 证据 `server/test/cors-preflight.mjs`（9/9）

| 断言 | 内容 |
|---|---|
| P1 | 预检返回 204（钩子已注册且在 OPTIONS 上收口） |
| P2 | 按源回显 `Access-Control-Allow-Origin=harbor://app` |
| P3 | 允许头逐项包含 `bridge.js` 发的那四个头（**缺一个即工具链路全断**） |
| P4 | 允许头不含通配符 `*` |
| N1/N2 | 非法源 `https://evil.example` 拿不到 origin、也拿不到 headers |
| P5 | UI 直调路径（只请求 `content-type`）仍 204 且放行 `content-type` |
| P6 | `file://` 调试源 `null` 按配置放行，且响应带 `Vary: Origin` |
| **S1** | **源码级对齐**：`bridge.js` 里 `headers[..]` 赋值的每个头都在 `app.js` 白名单中 |

S1 是防"下次加头又忘了改服务端"的那道闸——它读源码，不读配置。

### 1.5 ⚠ 边界：已装好的 v1.9.0 **同样受影响**

已安装的 `D:\harbor` 里 asar 中 `app.js` 也是 `content-type`。**修了源码不等于修了用户机器上的应用**，必须重新打包分发（见 §8 未决项）。

## 3. ③ 窗口背景不透明，显不出桌面

### 3.1 真根因：有生产、无消费

R80/W2 那条链**一直在正常工作**：

```
注册表 → TranscodedWallpaper → base64 data URI（~3MB）
  → electron/main.js 发 harbor:wp IPC
  → electron/preload.js:69-75 把 --wp-url / --wp-size / --wp-x / --wp-y / --wp-visible 写到 :root
  → ✗ 没有任何 CSS 规则消费它们
```

`grep -c -- "--wp-" harbor.html` 改前 = **0**。原生壁纸取到了、传到了、写进变量了，**然后没人读**。所以用户看到的是固定渐变，不是桌面。

### 3.2 为什么不直接开透明窗口

`backdrop-filter` **采不到 Windows 桌面**：透明窗口下它只能采样窗口内已绘制的内容，桌面不在合成树里。所以"透出桌面"只能靠**自绘镜像层**，不能靠真透明。这条决定了修复方式是"把镜像贴到氛围层"，不是"调 `transparent: true`"。

### 3.3 修复（`frontend/styles/responsive.css`）

新增两组**门控规则**（原有 3 条渐变规则一字未动，作为回退路径）：

```css
html[data-skin="lightwell"][data-wp="ready"] #lw-ambient-wallpaper{ /* 壁纸 + 3 层赤陶渐变 */ opacity:.62 }
html[data-skin="lightwell"][data-wp="ready"] body.dark #lw-ambient-wallpaper{ /* 暗档渐变 */ opacity:.65;
  background-blend-mode:normal,normal,normal,normal }
```

三个必须解释的决定：

- **门控是 `[data-wp="ready"]`**，不是 `--wp-visible`。壁纸读不到时 `data-wp="none"`，规则整体不匹配 → 自动回落到纯渐变，静默降级。
- **明档显式禁止 `background-blend-mode`**：有人提过用 `lighten` 把色差做到 Δ=0.00，但 `lighten` 是逐通道取最大值，会**抹掉深色壁纸**（用户桌面是深绿色海面）。Δ=0.00 是"把我测量的对象抹掉"才成立的恒真式，已否决。
- **暗档必须显式写 `normal`×4**：否则明档的声明会被继承。而 `normal` 是 CSS 默认值，光看 computed 抓不到"声明被删"——所以这条只能在**静态声明层**判。

### 3.4 代价（未结）

壁纸压上来后正文对比度下降。**三套测量口径给出三个不同数**（解析式 4.46 / 合成背景 4.79 / 真实像素 3.93），落地后的一轮实测又更低，但**本轮没有把最终值固化成证据文件** → 见 §8-A，属待真机复测项，本文不给具体数字。

### 4.2 修复

```css

                        inset 1px 0 0 rgba(255,255,255,.52),    /* 左：次强 */
                        inset 0 -1px 0 rgba(150,198,255,.26),   /* 底：冷色反射 */
                        inset -1px 0 0 rgba(255,255,255,.28);   /* 右：最弱 */
/* 暗档 */ 同一结构，四个 alpha 全部降到 .22/.13/.10/.07
```

### 4.3 为什么 `--glass-blur` / `--glass-saturate` 一个字节都不能动

## 7. 判据工程教训（本轮新增，接 R97 §四 的 24 条）

1. **"能力已建成"≠"接线已通"**。①②③ 三个缺陷同型：功能有、变量有、函数有，**消费点为零**。查这类问题最快的动作不是读实现，是 `grep -c` 那个符号在产物里出现几次——0 就是断线。
2. **断言对象必须是真实调用链**。`groupContextFor()` 是个纯函数，测它等于测一个可能没被任何请求用到的孤儿。必须抓出站请求体的 `messages[0].content`，并断言它**逐字符等于**产品自己算出来的值（`body === expect`）。
3. **参数正确性要能被构造性证伪**。①②③ 都能被"在 sys 末尾硬拼一段 `hubCatalogPrompt(picks[currentSessionId])`"这种近似实现满足；只有 N4（`picks[s.id]` 有值 + `currentSessionId` 指向别处）能区分"用了 `s.id`"和"用了当前会话"。**没有这条，抄个无参版也能全绿。**
4. **"运气通过"必须标注为运气**。工程师的早期探针能抓到无参版，仅因为用例 `SID` 恰好不等于环境会话键。已在覆盖边界里明写"该维度依赖环境键巧合，由 N4 构造性覆盖"。**把运气写进"已覆盖"，等于给自己发假合格证。**
5. **被测对象可能在跑的过程中变化**。群聊 system 提示是**有状态**的：每轮结束 `groupArchiveHandoff()` → `s.groupFiles` 增长 → `groupFilesContextLines()` 把最新 12 条拼进 sys。实测 sys 长度 1094 → 1515 → 4003。任何"A 场景 vs B 场景"的逐字节比对，只要中间跑过一轮，基线就脏了。**基线必须同状态现算，不能跨轮复用。** 这与 R97 的"transition 过渡值""computed 读默认值"是同一类坑。
6. **改 token 会连锁打翻别处的逐字符 pin**。`liquid-switch-probe.mjs:9` 钉死 `'blur(14px) saturate(1.18)'`，调 `--glass-saturate` 直接判红。**动任何 token 前先 grep 这个 token 有没有被逐字符断言过。**
7. **同一份文件里可能并存相反的预处理要求**。变异要喂"剥注释文本"（防打偏到注释），但皮肤段定位靠注释 `LIGHTWELL R90`，剥了它门禁第 1 条就报"未识别到皮肤段"。**任何"先剥注释再判"的预处理都会误伤把注释当锚点的判据**——这是本仓的设计债。
8. **计数口径必须写明**。`--wp-` 本轮出现"工程师报 8、我报 6"的假冲突，两个都对：`grep -c` 是命中**行数**（产物被压缩成少数行），`grep -o | wc -l` 是**出现次数**。不写口径的数字，隔一轮就变成争吵。
9. **锚点演进要证明"没多改"**，而不是只说"我改了这一处"。本轮用**隔离重建**做归因：只换一个文件，能从旧产物逐字节复现旧 sha → 反证其余源码零漂移。这比"我只改了一个函数"的自述强一个量级。
10. **补丁没跑过就等于没给**。本轮工程师给 QA 的止血正则 `String(0.62).replace(/^0\./,'')` 得到 `'62'`，拼出来只匹配 `opacity:62;`，对 `.62` 返回 false。QA **没照抄**，改用解析派生。规则：**发出补丁前先自己跑一遍**。
11. **期望值本身也可能是错的**。我给 QA 的验收表预期 T2 为 `19/2`，实测 `20/1`——因为我的表是照"旧版负控会跟着崩"写的，锚点改成解析派生后负控不该崩。**QA 按实测报而不是照抄我的表，这是对的。**
12. **比对字段要穷举，不能挑着比**。我第一次核 r89→r98 只比了 4 个字段就下结论"只改了行多重集"，漏了 `function_defs`（QA 挖出来的）。改判为"行多重集 + 精确 1 个函数体"。**漏一个字段，结论就从"精确"退化成"模糊"。**
13. **两个数相减凑出一个公式，是算术反推，不是测量**。本轮为解释 `1094 − 981 = 113`，先有"来自一条群文件条目"、后有"来自名册差"，**两个都是拿差值反凑的**，都被对方的复算打掉。最终交接文档写的是「剩 31 未定位，不写原因」。**宁可写"未定位"，也不要写一个评审一验就露的解释**——尤其当这个解释只影响一句说明文字、却有污染后续判断的风险时。
14. **同一结论要两条独立路径才能签收**。本轮做到的：产物差量归因（工程师与 QA 各自重建出 `6144bc94…`）、SEG 段长（各自算得 2764）、锚点差异面（我比 4 字段、QA 挖出第 5 个）、`Δws = len(wsRoot)+29`（工程师 5 态、QA 3 态）。**没做到两条路径的，都标成"未定位"而不是"已确认"。**
