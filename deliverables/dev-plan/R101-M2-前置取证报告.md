## E5 · 真实中文 IME 候选框定位做不到

三层原因叠加：
1. 无桌面交互会话，无法安装/驱动微软拼音或搜狗候选窗；
2. 候选窗是 TSF/IMM32 的独立 top-level window，不是被测窗口子窗，无法稳定归属到某个输入框；
3. 判定"错位 ≤2px"需要输入框 caret 的真实屏幕坐标，而 caret rect 只能由 Chromium 内部给出。

**结论**：必须 blocked-by-environment。**不得为凑齐维度造合成得分。**

## E7 · OSR 共享句柄字段名（源方案写错了）

**探针**：`osr-probe2.js`

**原始输出（`textureInfo` 全量键名）**：
```json
["pixelFormat","codedSize","visibleRect","contentRect","timestamp",
 "colorSpace","widgetType","metadata","handle"]
```

**句柄样本**：
```json
{"bytes":8,"expectHandleSize":8,"hex":"8c0f000000000000","asBigUint":3980,
 "codedSize":{"width":640,"height":482},"pixelFormat":"bgra"}
```

**结论**：
- 共享句柄在 **`textureInfo.handle.ntHandle`**（8 字节 Buffer = x64 `sizeof(HANDLE)`）；
- **不存在** `textureInfo.sharedTextureHandle` —— 源方案 §2.2 的写法会恒 false，**静默跳过、不报错**；
- 这是个高危静默失败点（记为 R1）。

## E8 · OSR 出帧条件

**探针对照**：

| 版本 | 条件 | 结果 |
|---|---|---|
| v1 | 静态页面，未 `startPainting` | 只出 1 帧，1 帧带 texture |
| v2 | 静态页面 + `startPainting` + 反复 `invalidate()` | 100 帧 / **1 帧**带 texture |
| v3 | 静态页面 + 串行 `invalidate()` 等上帧 | 90 帧 / **1 帧**带 texture |
| v4 | **加 rAF 动画** + `startPainting` | 204 帧 / **170 帧**带 texture |
| v5 | 同上，实测 2.5s | 201 帧 / **168 帧**（83.6%） |

**结论**：
- 必须 `win.webContents.startPainting()`；
- **页面必须有真实视觉变化**（静态页面即使反复 invalidate 也不出新帧，Chromium 判定无脏区、合并重绘）；
- 「能出 1 帧」看起来像可用，实际完全不能用于实时透色 → 记为 R2。

## E9 · 原生吃下 Chromium 纹理（通路 B 的成败闸门已打通）

**探针**：`osr-probe2.js` + `gyp/probe_addon.cpp`（N-API addon）

**原始输出**：
```json
{"handleBytes":8,"handleValue":3908,"qiDevice1Hr":0,
 "openSharedHr":0,"openOk":1,
 "width":640,"height":482,"format":87,"mipLevels":1,"sampleCount":1,
 "bindFlags":40,"miscFlags":2050,"usage":0,
 "srvHr":0,"srvOk":1,
 "stagingHr":0,"mapHr":0,
 "centerPixelBGRA":"255,255,255,255"}
```

**解读**：
- `openSharedHr=0` → `OpenSharedResource1` 成功；
- `format=87` = `DXGI_FORMAT_B8G8R8A8_UNORM`；

- `mapHr=0` + `centerPixelBGRA=255,255,255,255` → 真读到了像素内容，**不是空纹理**。

**结论**：通路 B 的最大技术未知（原生能否吃下 Chromium 纹理）**已消除**。裁决只剩性能与手感，不是可行性。

> **但探针通 ≠ Demo 成立**。本项只证明"吃得下"，P0-3 还要证明"持续吃得下"。

## E10 · N-API addon 构建链（手工 cl 会静默崩溃）

**现象**：

| 构建方式 | 系统 Node 22 | Electron 45 |
|---|---|---|
| 手工 `cl ... /LD /MD` | ✅ 加载正常 | ❌ **加载即崩溃，无报错** |
| `node-gyp` | ✅ | ✅ |

最小 addon（只返回一个字符串 `"hello"`）在 Electron 下手工编译版崩溃：连 `STEP2` 都不打印，`process.exit` 不执行。

**根因**：缺 node-gyp 自动生成的 `win_delay_load_hook.cc`。

**第二个坑**：`binding.gyp` 未加 `"/utf-8"` 时，MSVC 按 GBK 解析 UTF-8 中文注释，某些汉字尾字节是 `0x5C`（反斜杠）→ 把**下一行整行注释掉** → 报假 `C2065: srv 未声明`（实际丢了两行 `ID3D11ShaderResourceView* srv` 的声明）。

**正确命令**：
```bash
node node_modules/node-gyp/bin/node-gyp.js rebuild \
  --runtime=electron --target=45.2.1 \
  --dist-url=https://electronjs.org/headers \
  --arch=x64 --devdir="$LOCALAPPDATA/electron-gyp" \
  --directory=native/build/m2probe/gyp
```

**结论**：M2 起 addon 一律走 node-gyp；`binding.gyp` 必须含 `/utf-8`；独立 exe 继续走手工 cl（两条链并存）。

## E13 · 帧周期换算

165Hz → 一帧 **6.06 ms**。

源方案「DisplayLatency ≤ 12.5ms（120Hz 分母）」在本机口径下 ≈ **2.06 个帧周期**。

**结论**：绝对毫秒红线在本机口径不对。操作性指标应改为**以帧为单位的 P95/中位数比较**，不再用绝对毫秒判定通过。

## E14 · A/B 共用采集器（99/99）——**含一处自我更正，见 E14b**

**探针**：`collector.cpp`（CPU QPC + GPU Timestamp Query + 帧序号）

**四版迭代**：

| 版本 | 采集方式 | GPU_VALID |
|---|---|---|
| v1 | 紧凑 `for` 循环，立即 `GetData` | **1 / 100（1%）** |
| v2 | ping-pong 双查询组 + `Sleep(1)` 有界等待 | 55 / 100（55%） |
| v3 | 三组轮转（读两帧前） | 54 / 100（54%） |
| v4 | **按 Waitable 帧节拍推进** | **99 / 100（99%）** |

**v4 首次读数**（**注意：此读数后来被 E14b 判定为口径错误，不可作性能证据引用**）：
```
FRAMES=100  GPU_VALID=99  (99%)
CPU_FRAME_MS  p50=0.3292  p95=1.2358  max=1.5214
GPU_WORK_MS   p50=0.3132  p95=1.2258  max=1.5471
DIAG tried=99 disFail=0 freqZero=0 disjoint=0 stampFail=0 stampZero=0
VERDICT_COLLECTOR=SHARED_COLLECTOR_USABLE
```

**v1–v3 的根因（仍然成立）**：`disFail=0 / freqZero=0 / disjoint=0` 但 `stampFail` 高，逐次查询是 `h0=S_OK, h1=S_FALSE` —— 区间起点 t0 已完成、**终点 t1 尚未完成**。紧凑循环里 CPU 提交速度远快于 GPU 完成速度，队列越积越长，`Sleep(1)` 追不上。所以「按 Waitable 推进」这个方向是**对的**。

**但 v4 的 `GPU_VALID=99` 被当成了「采集器已可用」的证据 —— 这一步是错的，见 E14b。**

## E14b · 🔴 **自我更正：`Present1(0, …)` 让整条链没等 vsync**

**触发**：架构师指出 `collector.cpp` 里那条交换链**从未 `SetContent`/`SetRoot`/`Commit` 到任何 target**，并据此推断「`Present1` 根本没等 vsync，证据是 `p50=0.3292` —— 若真按 165Hz 推进必须 ≈6.06ms」。

**核实结果：架构师的观测事实成立，但归因错误。**

我用 `grep` 复核了他的事实：`collector.cpp` 里确实一处 `SetContent`/`SetRoot`/`Commit` 都没有。但「没接合成树」不是根因。**真正的根因是 `Present1` 的第一个参数 `SyncInterval` 写成了 `0`**，而 `0` 的语义是「立即返回，不等垂直同步」。

**六组对照实测（`calib.cpp`，N=180，本机 2560×1440 @165Hz）**：

| 组 | 交换链类型 | 接 DComp | SyncInterval | p50 | 实测 fps | 判定 |
|---|---|---|---|---|---|---|
| CAL-1 | `ForHwnd` | — | 0 | 0.1536 ms | 1538 | ✗ 未钉住 |
| CAL-2 | `ForHwnd` | — | **1** | **6.0594 ms** | 162.0 | ✓ |
| CAL-3 | `ForComposition` | 否 | 0 | 0.1537 ms | 2125 | ✗ |
| CAL-4 | `ForComposition` | **是** | 0 | 0.1786 ms | 3352 | ✗ |
| CAL-5 | `ForComposition` | **是** | **1** | **6.0596 ms** | 165.9 | ✓ |
| CAL-6 | `ForComposition` | 否 | **1** | **6.0644 ms** | 165.9 | ✓ |

**决定性证据**：CAL-4 与 CAL-5 是**完全相同的代码**，唯一差别是 `SyncInterval` 从 0 改成 1；接没接合成树毫无影响（CAL-5 vs CAL-6 都 ≈6.06ms）。**因此「接合成树」与「节拍」无因果关系。**

**修正后读数**（`Present1(1, 0, &pp)`，其余不变）：
```
FRAMES=100  GPU_VALID=99  (99%)
CPU_FRAME_MS  p50=6.0643  p95=6.1391  max=6.2358
GPU_WORK_MS   p50=6.0301  p95=6.1909  max=7.3943
DIAG tried=99 disFail=0 freqZero=0 disjoint=0 stampFail=0 stampZero=0
VERDICT_COLLECTOR=SHARED_COLLECTOR_USABLE
```

`p50=6.0643ms` 相对 165Hz 理论值 `6.0606ms` 偏差 **0.06%**；`GPU_WORK_MS` 与 `CPU_FRAME_MS` 量级一致（都是 6ms 级），说明此时测的确实是**每帧占满一个显示周期**，而不是 CPU 空转速度。

**排除了的其他假设（都做了实测，不是推理）**：
- 假设「DWM 没在采样这个窗口」→ `DwmGetCompositionTimingInfo` 全程 `rateRefresh=10000000/60604`（=165.0Hz）、`IsCompEnabled=1`；但 `cRefresh` 每 Present 一次只 +1、`cFrameDisplayed` 恒为 0 —— 这**是** `SyncInterval=0` 的结果，不是原因。
- 假设「进程不在可交互窗口站」→ `dwmpace`/`ctxprobe` 实测 `WindowStation=WinSta0`、`Desktop=Default`、`OpenInputDesktop=OK`，且 `CreateWindowEx(WS_VISIBLE)` 后 `IsWindowVisible=1`、`SM_CXSCREEN=1707 SM_CYSCREEN=960`。**不是沙箱问题。**
- 假设「`WaitForSingleObjectEx` 返回了 TIMEOUT 被我们忽略」→ `waitsem.cpp` 逐帧打印返回码：`OBJECT_0=10 TIMEOUT=0 OTHER=0`，`WAIT_MEAN_MS=0.001`。**是真放行，不是超时。**

**教训（并入 §五 判据工程教训）**：
1. **`Present1` 的 `SyncInterval` 是「节拍成立」的唯一开关，且它不会被任何 HRESULT、任何 DWM 查询、任何「看起来在动」的现象暴露。** 六项指标全绿（HRESULT 全 0、`GPU_VALID=99%`、`cRefresh` 在涨、进程退出码 0、`Wait` 全 `OBJECT_0`）而节拍完全不成立 —— 这是 R6 的**实证样本**，不是假想。
2. **反例注入必须注入到「被测属性本身」**。架构师提议的负控「去掉 `Commit()`」在本机测不出差异（CAL-5 vs CAL-6 同为 6.06ms），因为 `Commit` 不控制节拍；真正有效的负控是「把 `SyncInterval` 改回 0」。
3. **先标定仪器，再测对象**（教训 18 的再次验证）：`CAL-1↔CAL-2` 这条「标准 HWND 交换链」空对照是整轮取证里最有价值的一步 —— 没有它，我无法区分「对象有问题」和「仪器有问题」。

**对上游文档的影响**：`R101-M2-Spike-PRD.md` 的 R5（采集链必须按显示节拍推进）**方向正确但描述不完整** —— 它只说了「按 Waitable 推进」，没说「`SyncInterval` 必须为 1」。按 R5 字面实现会再次得到 `p50≈0.15ms`。**R6 应改写为「`SyncInterval=1` 且被 vsync 钉住」，并把 `PACE_OK` 判据锚定在 `|p50 − 1000/hz|/(1000/hz) ≤ 0.20`。**

## E15 · 🔴 **D2③「GPU 单帧时长」在 165Hz 满帧节拍下**无分辨力**（否决 Q3 备案）

**触发**：架构师 Q3 备案提议「D2 主统计量改为 GPU pass 墙钟 + CPU/帧」。我在 E14b 修正后看到 `GPU_WORK_MS p50=6.0301` 对 8 次 640×480 Clear —— 8 次 Clear 不可能占 6ms，怀疑这个读数测的不是「GPU 干活」。遂做底噪标定。

**探针**：`gpufloor.cpp`（三组判定，N=120，`ForComposition` + 完整 DComp 合成树 + `SyncInterval=1` + Waitable）

**判定一 —— 0 次 Clear 作空对照**：

| 组 | Clear | SyncInterval | CPU_FRAME p50 | **GPU_WORK p50** |
|---|---|---|---|---|
| F-0 | **0** | 1 | 6.0617 | **0.0005** |
| F-8 | 8 | 1 | 6.0594 | 6.0540 |
| F-64 | 64 | 1 | 6.0576 | 6.0267 |
| F-256 | 256 | 1 | 6.0710 | 6.0530 |

0 次 Clear 时 GPU_WORK = **0.0005ms**（几乎为 0，说明 query 区间本身是准的、有分辨力的）；一旦有 ≥1 次 Clear，立刻顶到 6.05ms 级并**完全不随负载变化**。这是典型的 ceiling effect：**query 区间被交换链的 vsync 等待吞掉了**。

**判定二 —— 1440×1440 负载扫描（找饱和边界）**：

| Clear | GPU_WORK p50 | 与刷新周期之比 |
|---|---|---|
| 0 | 0.0005 ms | — |
| 8 | 6.0382 | 1.00× |
| 192 | 6.0423 | 1.00× |
| 256 | 6.0645 | 1.00× |
| 320 | 6.0210 | 0.99× |
| 384 | 6.0329 | 1.00× |
| 448 | 6.0515 | 1.00× |
| 512 | 6.0232 | 0.99× |
| 640 | 6.0757 | 1.00× |
| **768** | **12.1101** | **2.00×** |
| **1024** | **12.0979** | **2.00×** |

**8 次 → 640 次，负载增加 80 倍，读数在 6.021–6.076 之间抖动（极差 0.9%）；越过某条边界后直接跳到 12.10（= 2 × 6.06）。中间没有任何过渡值。**

**结论：在 `SyncInterval=1` 满帧运行时，GPU pass 墙钟的分辨率 = 1 个刷新周期（6.06ms）。** 读数被量化成 `k × 6.06ms` 的离散档，任何「两者 GPU 开销差 0.5ms」的结论在物理上不可测。**相对误差 ≈ 100%**，远大于 D1/D2 要求的 `Δ > N`。

**判定三 —— 关闭 vsync 作正样本（证明仪器本身没坏）**：

| 组 | Clear | SyncInterval | GPU_WORK p50 |
|---|---|---|---|
| G-8 | 8 | 0 | 0.1878 |
| G-256 | 256 | 0 | 1.1626 |
| G-1024 | 1024（1440px） | 0 | 8.0739 |

`SyncInterval=0` 时负载敏感恢复正常（0.19 → 1.16 → 8.07，单调且跨度 43 倍）。**这证明 query 机制本身是准的，问题只出在「满帧节拍下测量」这个组合。**

**三条结论**：

1. **Q3 备案不成立，必须否决。** 「D2 主统计量改为 GPU pass 墙钟」在 165Hz 下等于把主统计量换成一个**分辨率为 6.06ms 的阶梯尺**。A/B 两条通路只要都满帧（这本就是期望状态），D2③ 必然双双落在同一档 6.06ms，`Δ = 0`，永远 `tie`。这不是「测出来一样所以不可区分」，是「仪器精度不够所以必然不可区分」—— 后者是**假 tie**，比假绿更隐蔽。
2. **D2 主统计量必须换回 CPU_FRAME / Present 间隔分布**（D2① 原设计），因为它在 `SyncInterval=1` 下同样被钉在 6.06ms —— 但那**是正确语义**（帧确实按 vsync 交付），而 `p95`/`p99`/max 与掉拍率（D2②）才是有分辨力的量：掉到 12.12ms 就是掉一拍，掉到 18.18 就是掉两拍，**掉拍率的分辨率恰好等于 1 拍，正好与 D2② 的判据（`p99 ≥ 2×vsync 基准`）匹配**。
3. **D2③ 只能作为「结构性旁证」保留，且必须改口径**：不得报绝对值，只能报「落在 k×周期 的哪一档」（`k=1` 满帧 / `k=2` 掉一拍 / `k≥3` 长空洞）。这与 PRD 现有 D2③ 的「结构性旁证」定位一致，但必须**明写它不可用于 Δ/N 比较**。

**对 PRD 的影响**：`R101-M2-Spike-PRD.md` D2 行 ③ 需加注「**在 165Hz 满帧节拍下，本项分辨率为 1 个刷新周期，不得用作 Δ 比较输入；仅作 k 档结构性旁证**」。D2 主统计量明确为 ① Present 间隔分布 + ② 掉拍率。

**方法论价值（并入教训）**：
- **「0 次作空对照」是发现 ceiling effect 的唯一手段。** 我没有一开始就怀疑 GPU_WORK，是 F-0 组的 0.0005ms 与 F-8 的 6.0540ms 之间那道断崖暴露了问题。若我只跑 F-8/F-256 两组，会看到「6.0540 vs 6.0530，差 0.02%，判 tie」—— 而真正的结论应该是「仪器在这里没有分辨率」。
- **「负载扫描找不到单调段 = 仪器失分辨力」，不是「对象差得小」。** 判定二扫了 9 档，8→640 全平，这是判别依据。单点比较永远分不出这两种情况。

## E16 · DDA（Desktop Duplication）可用 —— T02 的 `DDA_SELFTEST` 前提成立

**探针**：`ddaprobe.cpp`（`DuplicateOutput` + 自建 DComp 窗口涂纯品红 + 回读中心像素）

**读数**：
```
D3D11CreateDevice hr=0x00000000 FL=0xB000
Picked adapter=0 output=0 \\.\DISPLAY1 attached=1
DuplicateOutput hr=0x00000000 (OK)
Duplication desc: 2560x1440 mode=0 Rotation=1
  SM_CXSCREEN=2560 SM_CYSCREEN=1440
  DEVMODE orient=0 2560x1440  dmDisplayOrientation=0
Our window at (200,200) 320x320
  frame#1 surf=2560x1440  center(360,360) BGRA=255,0,255,255
  ... frame#5 同上
RESULT: gotFrames=5  magentaHits=5
DDA_SELFTEST=PASS
```

**结论**：
- `DuplicateOutput` 在本机（Intel Iris Xe 输出 0，2560×1440@165Hz）**可用**，`hr=0`；
- 抓到的 frame 为 **2560×1440 全屏**，**桌面坐标可直接寻址**（窗口在 200,200 尺寸 320，中心 360,360，读到的正是品红）→ **无需旋转/缩放换算**；
- `Rotation=1` 是 **`DXGI_MODE_ROTATION_IDENTITY`**（枚举序 0=UNSPECIFIED, 1=IDENTITY, 2=ROTATE90…），**不是"旋转 90 度"**。若按字面理解成旋转，会引入一个不存在的坐标变换 bug。DEVMODE `dmDisplayOrientation=0`（DMDO_DEFAULT）二次确认。

**由此确定 T02 的 `DDA_SELFTEST` 设计**：
- 正样本 = 涂纯品红 → 抓帧 → 中心像素 `BGRA=(255,0,255,255)` → PASS（已实测）
- **必须配的负控 NC-A1′**：把 `Present1` 那行注释掉（保持 `Commit` 与窗口在）→ 抓帧应读到**桌面背景**而非品红 → 自证必 FAIL。若此负控仍 PASS，说明读到的是别处（例如上一次残留的合成内容），自证链失效。

## E16c · 🔴 **DDA 能抓到 Electron/Chromium 窗口 —— 推翻 T03 的「抓不到」结论**

**触发**：T03 工程师在交付报告里给出裁决项「**DDA capture of Chromium content did not even get attempted**，D1 对 A 通路应降为 `blocked`」。这条如果成立，D1（层间对齐，权重 30）就整条退出裁决，覆盖率从 80% 掉到 50%。

**探针**：`dda_win.js`（起对照窗口）+ `dda_electron.cpp`（抓帧）+ `dda_fix.cpp`（修正判据）。四种形态：

**结论：DDA 对 Electron 内容（含 OSR 透明覆层）可用，D1 不必降为 blocked。**

### 但这里有一个我自己犯的「断言恒真」，必须记下来

第一版探针 `dda_electron.cpp` 的判据是 `frames > 0 && nonBlack > 0` → `VERDICT_DDA_CAPTURED=YES`。**形态 C（隐藏窗口）也被判成了 `YES`** —— 因为壁纸 `(20,20,20)` 不是全黑。

**判据只判了「不是黑的」，而壁纸也不是黑的。** 这是教训 1 的又一实例：**判据的分辨力边界恰好被背景色穿过**。

**修正后的判据（`dda_fix.cpp`，两条合取）**：
1. **颜色命中**：`|实际 − 预期| ≤ 10`（每通道）
2. **坐标在窗口矩形内**：读取坐标必须落在 `GetWindowRect` 内

**修正后实测分辨力**：

| 形态 | `CRIT_COLOR` | `CRIT_INRECT` | `DDA_SELFTEST` |
|---|---|---|---|
| A 可见 | `11/12` PASS | `1` PASS | **PASS** |
| C 隐藏 | **`0/12` FAIL** | `1` PASS | **FAIL** |

**关键点：`CRIT_INRECT` 在两种情况下都是 PASS。** 它单独完全恒真 —— 只有与 `CRIT_COLOR` 合取才有分辨力。**这说明「坐标在矩形内」不能单独当防线，它只能防「读到别处同色像素」这一种特定错误。**

### 对 D1 的影响

- **D1 保持 A 类（可测，权重 30）**，覆盖率维持 **80/100**
- T03 那条「D1 降 blocked」**作废**
- 但 D1 有一个**真实的前置风险**：D1 要求「同一抓取帧内解出两层各自的 `(frameIdx, qpcLow)`」，这需要**两层同时可见**。形态 B/OSR 的覆层窗口若 `transparent:true` 且背板由 DComp 原生窗绘制，两层是**两个独立 HWND**，DDA 抓到的是 DWM 合成后的**结果**，不是两层各自的内容 —— **Δpx 判据需要的「同一帧内两层各自基准标记」可能无法分离**。

**这一条我还没测，是 D1 剩余的唯一真风险。** T02/T03 交付后需实测「双窗叠加时能否在同一抓取帧内分别识别两个基准标记」。若能，D1 完全可用；若不能，D1 需降级为「只能测合成后结果，不能测层间偏差」，届时须报主理人重新裁决权重。

## E16b · 🔴 **DPI 感知状态会让 `SM_CXSCREEN` 差 1.5 倍，且 DDA 自证会「静默通过」**

**触发**：E16 探针报 `SM_CXSCREEN=2560`，而同一环境下 `ctxprobe` 报 `1707`。两个数差 1.5 倍，必须查清。

**探针**：`dpiprobe.cpp`

**读数**：
```
awareness(before) = UNAWARE
SM_CXSCREEN=1707 SM_CYSCREEN=960          <-- 虚拟化后

after SetProcessDPIAware():
awareness = SYSTEM_AWARE
SM_CXSCREEN=2560 SM_CYSCREEN=1440         <-- 真实

DEVMODE 2560x1440 @ 165Hz orient=0
GetDpiForMonitor effective = 96 x 96
scale = 1.000
```

**结论**：
1. **进程默认 DPI 感知 = `UNAWARE`**，此时 `GetSystemMetrics(SM_CXSCREEN)` 返回的是**被 1.5 倍虚拟化的逻辑尺寸 1707×960**，不是物理 2560×1440。
2. `GetDpiForMonitor(MDT_EFFECTIVE_DPI)` 在 `UNAWARE` 进程下**也返回 96×96**（虚拟化后的值），**不能用它判断"有没有缩放"**。真实缩放是 1.5（=2560/1707）。
3. **DDA 抓到的 surface 永远是物理 2560×1440**。所以：
   - `UNAWARE` 进程若用 `SM_CXSCREEN`（1707）去算窗口落点或换算像素坐标 → **整体偏 1.5 倍**；
   - 更糟的是 **DDA 自证可能照样"读到颜色"** —— 只要那个偏掉的坐标落在同色区域（例如大片背景），断言依然 PASS，但读的根本不是目标窗口。**这是「断言恒真」的 DPI 变种**。

**对 T02 的硬约束（必须写进任务规格）**：
- `dcomp_host` 与一切参与坐标换算的原生模块，**必须在 `wWinMain`/`WinMain` 最开头调用 `SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)`**（失败则回退 `SetProcessDPIAware()`），并**断言调用成功**；失败路径要显式报错，不许静默继续。
- `DDA_SELFTEST` 的**判据必须是「读到预期颜色」+「坐标落在窗口矩形内」两条同时成立**，不能只判颜色。
- 新增**负控 NC-A1″**：故意把窗口位置与读取坐标**同时**偏移 1.5 倍（模拟 `UNAWARE` 下的错误换算）→ 自证**必须 FAIL**（因为偏移后坐标落在窗口外，读到的是背景）。若仍 PASS，说明判据只看了颜色、没看坐标。

**方法论价值**：这是「**同一份代码在不同进程状态下给出不同的正确性结论**」。DPI 感知是一个**全局隐含状态**，不影响任何返回值、不产生任何错误码，只悄悄改变坐标尺度。凡是「用系统坐标去比对屏幕内容」的判据，都必须先断言 DPI 感知状态。
