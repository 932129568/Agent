## 方向二：运行速度提升（F2）

**F2a 启动与就绪（25 轮）** — `F2a-startup.md`
- require() 同步递归阻塞是 Electron 启动头号瓶颈（官方实测 request≈500ms vs node-fetch<50ms）；main 进程 require 体检+先窗后服务。
- 3.8MB 内联 script 无法 defer（1MB≈300ms 解析）；IIFE 单包不可拆，拆包依赖 ESM 改造。
- fastify 启动主导项=JSON Schema 编译（两阶段编译可把启动变常量，100 schema≈100ms）；NODE_COMPILE_CACHE 可启用。
- WebView2 冷启动靠 UDF 持久化+避免冗余实例；renderer 改走 127.0.0.1 或自定义协议解锁完整 timing。
- 争议：中文案例「禁硬件加速 -20~40%」与微软官方「GPU 至关重要」冲突——对 Harbor 截图/捕获不建议采用。
- **Harbor 建议**：启动时间线打点基线、ready-to-show+超时兜底防白屏、115 模块首屏/非首屏分层懒执行、/healthz 就绪轮询+loading 页先行。

**F2b 数据层（25 轮）** — `F2b-data-speed.md`
- 关键边界实测：<2000 条+读多写少 JSON 全读快 4x；写频繁 SQLite 快 30x；10k 条 JSON 全读 60ms+15MB 堆峰值——Harbor 17.3MB sessions.json 已超 JSON 优势区。
- WAL 写吞吐 10x+；synchronous NORMAL 快 17x 但断电丢尾（消息类建议 FULL）；checkpoint 独立线程可让主线程零 fsync 阻塞。
- better-sqlite3 vs libsql：写快 24x、四驱动基准赢 8/12——纯本地场景 libsql 是负资产；Prisma 冷启 4-6s。
- V8 已把 JSON.stringify 提速 2x——正解是**会话级脏标记增量持久化**，而非换编码/换库。
- 防抖必达双保险：maxWait 硬上界（≤3s）+ before-quit/pagehide 强制 flush。
- **Harbor 建议**：消息按会话键控存储、批量事务、28 类文件分级存储、maxWait+flush、游标分页、user_version 迁移短路。

**F2c 构建与测试链路（25 轮）** — `F2c-build-test-speed.md`
- pytest 提速：xdist 单项 50-80% 缩水（PyPI 案例 163s→30s）；时长不均套件首选 `--dist worksteal`；Windows worker spawn 贵（15 worker≈+8s）、无 fork、有官方挂死 issue #60——先实测，净收益不足 2x 则退 pytest-split matrix 分片（durations 文件入库、两周一更）。
- Windows 坑：GBK 统一解 `PYTHONUTF8=1`；session/autouse fixture 在 xdist 下每 worker 各跑一次，需 worker_id 命名空间+filelock。
- CI：setup-python/node 内建缓存先行；pip TEMP 指 SSD 提速 30%；每 job timeout-minutes+cancel-in-progress 防挂死。
- 分层与重试：smoke(<2min 每提交)→PR 全量→夜间全量；rerunfailures 主流折中=可重试但必须上报重试计数（flaky 率可见化）。
- 构建链：增量指纹以内容哈希为准；Harbor 双跑幂等可升级为「双跑+sha256 门禁+diffoscope 定位漂移」，发布侧加 re-hash 闸门。

**F2d 前端加载/资源（25 轮）** — `F2d-frontend-loading.md`
- **最关键发现**：Chromium 的 V8 code cache 只对 http(s)/WebUI 启用，**file:// 永久无效**（crbug 40288216）；内联脚本历史上也不进 cache（新版 Inline Script Cache 用内容哈希补）。Harbor（file://+全内联 3.8MB）两条都不满足——二次启动吃不到反序列化提速（≈2×）。
- **最大单项改法**：宿主改用 WebView2 `SetVirtualHostNameToFolderMapping`（https 源）加载 harbor.html，不动 HTML 结构即解锁 code cache+正常缓存栈。
- 成本拆解：桌面急切解析 ~10-30ms/MB（3.8MB≈40-115ms 主线程）；执行已取代解析成主导（最高占加载 30%）；流式编译对内联脚本无效（Chrome 72+ 仅外链）。
- 库级：hljs common ~42kB vs 全量 400kB-1MB（core+registerLanguage 省 90%+，需关 auto-detect）——最典型瘦身点；marked+DOMPurify 合计小，留内联合理。
- IIFE 顺序产物按声明序即刻执行、无惰性语义——真正收益在把设置/市场/浏览器驱动模块初始化包成 `initXxx()` 由 idle 回调/首次进入触发（三层启动预算模式）。
- br/gzip 仅省传输，file:// 本地无意义；掘金实战：启动 JS 减 60-80% → 3.2s→1.1s。

## 方向三：各场景 CPU 性能优化（F3）

**F3a 渲染路径（25 轮）** — `F3a-render-cpu.md`
- 业界收敛=「块级冻结+尾部活动块重渲染」：Vercel Streamdown（memoization+LRU）、Cherry Markdown、掘金 7.8kB 自研渲染器同一路线；1 万字回复主线程 1.1s/最慢单帧 3.3ms vs 全量方案 6.4s/38.7ms（~6x）。
- 分块+增量解析把 2000 token 回复渲染 6s→1.5s；高亮每 token 重跑是卡顿主因（闭合后一次执行或移 Worker）。
- 低成本高收益：历史消息 `content-visibility:auto`（7x+ 渲染跳过）；批重建用 scheduler.yield() 分片。
- 争议：不必换 markdown 解析器（marked 已够快）；innerHTML vs morphdom 之争在「只动尾块」前提下消解。
- **Harbor 建议**：onDelta 全文重解析（D24 留档项）改块缓存增量；回流治理=读写阶段分离；虚拟列表 positions 缓存+RO 修正。

**F3b 流式解析与序列化（25 轮）** — `F3b-stream-cpu.md`
- SSE 解析：单 TextDecoder + `{stream:true}`、每 chunk 单遍扫描只留尾部行缓冲（「全量重 split」即二次方反模式）；中文跨 chunk UTF-8 必须流式解码。
- O(n²) 渲染：块级缓存（已闭合块不再动，只重渲染未闭合尾块）+ rAF 阀门（token 入 buffer 一帧一 flush）+ 禁 `innerHTML +=`。
- JSON.stringify：V8 13.8 同形对象 express lane 提速 2x+，replacer/pretty-print 仍走慢路径；正确缓存=**逐消息分段串缓存+段级失效**，非整对象缓存。
- Python：orjson 快至 stdlib 10x、msgspec 相当且带一步校验；PyInstaller 需 `--hidden-import`+锁 wheel+干净 venv（msgspec Py3.13 有 wheel 失败先例）。
- highlight.js：core 8.5KB + 按 `data-lang` 动态 import 语言包；Shiki 因 CPU 预算被实战弃用；DOMPurify 依赖 DOM 不能进 worker（与 provenance 红线交互）。
- 方法论：`electron --js-flags="--cpu-prof"` 产 .cpuprofile 直拖 DevTools；采样式 profiler 低估极短高频函数，需长录制+Bottom-Up。

**F3c Python/Node 侧 CPU（25 轮）** — `F3c-backend-cpu.md`
- orjson dumps 较 stdlib 快 ~10-13x、loads 2-6x；msgspec「解码+校验」≈ orjson 裸解码；两者 PyInstaller 均需 hiddenimports/collect-all。
- hashlib 仅 >2047B 输入释放 GIL——小参数哈希瓶颈在每次调用开销 → 合并 update+copy() 共享前缀；串行哈希链下 BLAKE3 无收益（<4KB 反更慢），维持 SHA-256。
- base64 编码器是 C 实现多 GB/s 非瓶颈，真瓶颈=+33% 体积×JSON 转义×桥上大字符串复制 → 大截图应改二进制帧或临时文件传路径。
- Windows Popen 逐次 spawn 昂贵（~40% 税）→ 池化复用；asyncio 子进程 > 线程池包裹；注意 Process 被 GC 会杀子进程。
- fastify：under-pressure 阈值 503+monitorEventLoopDelay p99 采样；fast-json-stringify ~2x 但 V8 2025 原生 stringify 已 2x，需按自家 Node 重测。

**F3d 内存/GC/泄漏面（25 轮）** — `F3d-memory.md`
- 方法论：三快照法（Loreena Lee）+Allocation timeline 蓝条+Retainers 最短引用链是 JS 侧黄金标准；Blob URL 内存不进 heap snapshot，须用 Chrome 任务管理器。
- base64 纯 ASCII 在 V8 是 1B/字符，但中文消息天然 two-byte（2×）；IndexedDB 应存 Blob 免 33% 税。
- 缓存治理四件套（硬上限/LRU/失效/指标）；实战案例：无界 Map→LRU(500+15min TTL) 4.2GB→312MB。
- 弱引用边界：WeakMap 非缓存（value 强持）、FinalizationRegistry 只能兜底（Cloudflare 2025 实证）——显式清理+Disposable 配对表优先。
- Python 侧：大 JSON 走引用计数释放；tracemalloc 快照 diff 是 win32 下唯一可靠泄漏判据；RSS 滞留≠泄漏。
- **Harbor 建议**：会话改磁盘驻留+64 条窗口、pendingShots 换 Blob 配对 revoke、CS.reg/tokens Map LRU 化、TaskRegistry 终态 ring buffer、预算线（20 次流程 post-GC 增长 <5MB、detached DOM=0）、V8 参数默认不动。

## 方向四：调度机制优化升级（F4）

**F4a 调度模式（25 轮）** — `F4a-scheduling.md`
- 循环熔断参数各家保守（LangGraph 25 步/OpenAI max_turns=10/AI SDK 默认 20）；「超限丢结果」公认坏体验，应可续跑。
- 并发仲裁三层叠加：优先级队列→token bucket（速率）→semaphore（在飞）；会话公平性按 token 计权（OSDI'24 VTC）。
- 退避黄金法则（AWS）：full jitter+cap+5~7 次+Retry-After/reset 头优先；429 与 503/529 分流计数。
- checkpoint≠durable execution 是最大争议：resume 需副作用幂等/结果回放（arXiv 2608.29381「执行连续性危害」）。
- 取消语义三层分离（排队出队/in-flight 协作检查点/finally 清理）；Celery 内存 revoke 不可靠是反面教材。
- 桌面端调度状态必须落盘（启动重排）；APScheduler 默认 1s misfire 会静默跳过任务。
- 国内：GLM 免费档实测约 1 并发/3-5 QPS。
- **Harbor 建议**：P0=RunRegistry 落盘化、退避升级 full jitter、取消语义三层分离。

**F4b 退避/限流（25 轮）** — `F4b-backoff.md`
- OpenAI/Anthropic 官方 SDK 口径一致：默认仅重试 2 次、指数退避 0.5s→8s 封顶、Retry-After 上限 120s（源码实锤）；Harbor 4s/12s/30s 固定阶梯明显更激进。
- AWS 权威仿真：full jitter 是无状态最优折中（Equal 几乎无效、decorrelated 需持久化状态且无生产级独立实测）。
- RateLimit 头草案 -11（2026-05）改单头 SFV（r/t/pk）；Retry-After MUST 优先，t 用 delay-seconds 防时钟偏差。
- 熔断关键争议：主流认为 429=配额耗尽不应触发断路器，只冷却 key/模型；503/529/超时才计入（典型 5 次/30-60s/半开单探针）。
- 智谱限流口径=**并发数**（非 QPS）按模型×权益等级；glm-4.5-flash 官宣 2026-01-30 下线自动路由 4.7-flash；DeepSeek 并发按账号粒度（多 key 同账号无效）。
- 本地端点：Ollama MAX_QUEUE 512 溢出返 503（默认 NUM_PARALLEL=1）——本地 503 应按「忙」短退避而非按「死」长退避。
- **Harbor 建议 P1**：退避改 full jitter（base 1s/cap 30s/≤6 次）、Retry-After 夹紧封顶 120s、429 与 5xx 分计数（429 只冷却 key 不污染端点健康度）；glm-4.5-flash→4.7-flash 别名收尾。

**F4c 取消/看门狗/恢复（25 轮）** — `F4c-cancel-resume.md`
- 取消语义：取消是请求非终态——abort 后必须 await 工具批 finally 清理再落 run.cancelled；OpenAI runner-lifecycle 的 immediate/after-turn 双档取消可直接借鉴。
- 快照边界：partialContent 之外还应入册——在途工具批（id/args/状态/幂等键）、待发队列、步骤回执、版本元数据；恢复按回执去重，零重放已完成工具（对比 LangGraph interrupt 整节点重跑）。
- 副作用：不可逆操作靠事前审批门控而非事后 saga；补偿登记必须先于前向动作持久化。
- UX：中性横幅「此回复可能不完整」+Continue（finish_reason==='length' 检测）；Claude Code 的 Esc 中断+排队输入+--resume 是取消 UX 基准。
- 看门狗：TTFT 可 30-60s+（5s 提示需区分「思考中」与故障）、idle 30-120s、心跳 15-30s；首字节超时与中途停摆应分通道。
- 截断 tool_calls：业界结论「整体重试优于拼接片段」——Harbor fillMissing 建议降级为展示兜底，恢复时对非法 JSON 整批重发。
- 国内：SSE 事件 id+Last-Event-ID 断点续传。
**F4d 桌面定时调度（25 轮）** — `F4d-scheduled-tasks.md`
- 竞品齐备：ChatGPT Tasks（NL 创建+管理页+push/email，按 plan 限 3/5/10/15）、Gemini scheduled actions、Claude Code（/loop+CronCreate 三原语，仅会话存活触发、无 catch-up、周期 7 天过期）。
- misfire 三档：grace 窗内 coalesce 并成一次/逐次补/超窗丢弃（APScheduler 术语）；用户侧共识请求 per-task `misfire_policy=run_once|skip|run_all_due`+max catch-up age+运行历史标注补跑（openai/codex#24327）。

- 客户端坑：setInterval 相对时间累积漂移+休眠停走；须主进程 cron 墙钟重算+powerMonitor 'resume' 对账；Win11 24H2 suspend 事件不可靠→状态持续落盘。n8n/BullMQ 默认均不回填。
- 会话关系：共识倾向「每次新会话+注入任务模板+上次结果摘要」防 context rot；续用原会话仅作可选项。
- 无人值守：工具面收紧（always 档交互工具禁用）、待审批任务转暂停态+通知；定时拉取外部内容扩大间接注入面（least-privilege+provenance）。

- 主题：`light-dark()` 2026 已 Baseline（约 90% 支持率），但 `color-scheme` 声明必须 `@supports` 包裹防「灰上灰」；TDesign/Arco 暗色与 Harbor `body.dark` 同构（CSS 变量双套值+属性切换）路线验证正确。
- View Transitions：同文档 VT 2025-10 已 Baseline（Firefox ~144 补齐），主题圆形揭示可全量启用，仅需 feature detect 直切降级。
- 动效：NN/g 正典 100-500ms（反馈≈100、面板 200-300、大位移 ≤400、退出比进入快 50-100ms）；三层令牌+stagger delay 令牌化与 Harbor `--dur-*`/MOTION 约定吻合。
- reduced-motion：约 25-30% 用户开启；「reduce, don't eliminate」分级降级为主流正典（保 opacity/颜色过渡、砍 transform/视差/smooth-scroll），一刀切 `*{animation:none}` 是反模式。
- 三态主题：system 默认态+matchMedia change 监听+head 内联阻塞脚本防 FOUC——反方 Lea Verou 两态论已存档为争议。
