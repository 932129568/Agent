## 1. 产品目标与唯一问题

### 1.1 产品目标（一句话）

在 M2 的三个里程碑（§1.4 的 M2-a/b/c）内，用**可复现、可审计、不可事后编造**的采集证据，在通路 A（双窗 DComp）与通路 B（Electron 45 OSR 单链共享纹理）之间产出一个**边界明确的裁决**——明确到"哪几条维度真测了、哪几条本机测不了、裁决结论覆盖了多少权重"。

### 1.2 本次 Spike 要回答的唯一问题

> **在同一份合成负载下，通路 A 与通路 B 在本机可观测的「层间对齐一致性」与「单帧开销」上，是否存在超出测量噪声的差异？若存在，哪一条占优？**

以下问题**不在本次范围**（写进来就会稀释有限的采集预算）：哪条更好维护、哪条更省电、哪条在 120Hz 上更好、哪条对未来功能扩展更友好、以及"看起来是不是更像 macOS 的液态玻璃"。

### 1.3 为什么必须先裁决再写业务光学代码

两条通路的**失败模式互斥**：A 的结构性缺陷是"两窗各自 Present，合成帧内可能出现时间不一致的两层"；B 的结构性缺陷是"UI 由 Chromium 渲染后离屏导出，caret 语义脱离 HWND"。前者影响整块玻璃的观感，后者影响每一个中文字。这两类缺陷的修复成本都在数千行量级，且方向相反。**先写光学代码再选通路 = 有一半工作量注定报废。**

### 1.4 执行口径：按里程碑组织，不按「72 小时」组织

源方案的 72h 是**排期假设**，本项目实际是「逐轮迭代 + 每轮全量门禁」，不可能连续跑 72 小时。因此 `72h` 只作为**文档里的设计工时估算**存在，**不作为执行约束、不作为验收依据**。

| 里程碑 | 内容 | 出口判据（缺一即未完成） | 时长参数 |
|---|---|---|---|
| **M2-a** | 两条通路各自的「能跑起来 + 能自证出帧」Demo | 通路 A：E1 链路 `HRESULT` 全 0 且有日志；通路 B：P0-3 四条持续出帧判据在 **60Hz 基线档**全过（`FAIL` 才阻断 M2-a）；165Hz 能力档另出结论，不过则记 `PASS_BASELINE_ONLY` 但仍算 M2-a 完成（§4.0b） | 单次跑 ≥10s |
| **M2-b** | A/B **同参数**采集，产出原始数据 | 同一负载参数 JSON、同一采集器版本、**同一采集节拍**（§4.1 R-4）；每通路 **3 轮**；产出 `timing.jsonl` + `sync.jsonl` + `env.json`；**且必须产出可用噪声 N（A/B 各 ≥3 轮、轮间离散度可算，见 P0-13）——缺 N 则 M2-b 不算完成**。<br>**注意两组采集不要混**：M2-b 的性能采集是 **60s × 3 轮**；D3 长稳是**独立的 10 分钟 × 3 轮**，产出 `soak.jsonl`。**两者不互相顶替**——60s 跑不出泄漏趋势，10min 长稳也不是性能对比样本 | 性能 **60s × 3 轮**；长稳 **10min × 3 轮**（均可配，不取 72h） |
| **M2-c** | 裁决报告 + blocked 清单 + 一票否决结论 | 报告模板 §A–§F 全填、两句强制声明逐字命中、覆盖率 80% 明示、5 条负控全绿 | — |

> **为什么坚持里程碑而不接受"72 小时"**：72h 是一个**无法被验证的时间量**——没人能证明"我们确实连续跑了 72 小时"，但每个人都能验证"3 轮 60 秒的数据是否齐、轮间噪声是否可算"。**用可验证的量替代不可验证的量，是防止"工期叙事"替掉"证据"的唯一办法。**

### 2.1 已知静默失败点（"不报错"≠"成立"，必须用正向断言打穿）

主理人两次 OSR 探针暴露出一类新的风险：**程序跑得很健康，但功能根本没成立**。这类失败不会出现在退出码、日志或异常里，只能靠正向断言抓。

| ID | 静默失败点 | 失败时的表现 | 必须写的正向断言（缺一即不算通过） |
|---|---|---|---|
| **R1** | `textureInfo` 键名照抄源方案的 `sharedTextureHandle` | `if (info && info.sharedTextureHandle)` 恒 false；无异常、无日志、只是永不进入分支。**看起来像"Electron 不支持"** | ① `textureInfo.handle.ntHandle` 是非空 Buffer 且 `byteLength === 8`（x64 `sizeof(HANDLE)`）；② 原生侧 `OpenSharedResource1` 返回 **0** 且 `IID_PPV_ARGS` 拿到非空 `ID3D11Texture2D`；③ `codedSize` 与实际窗口客户区尺寸一致 |
| **R2** | 静态页面 + 隐藏窗口 | 100 帧仅 1 帧带 `texture`；进程健康、退出码 0。**看起来像"能出帧"** | 持续出帧四条判据（见 §4 P0-3） |
| **R3** | `event.texture.release()` 漏调或异常路径漏调 | 前若干帧正常，随后句柄耗尽 → 掉帧或挂起，退出码仍可能为 0 | 带纹理帧数 **==** `release()` 成功数（差值必须为 **0**） |
| **R4** | **PresentMon 装得上、`--help` 正常、退出码 0，但采集 `access denied`**（E3）。这是新一类静默失败：**安装成功 ≠ 可采集** | 只跑 `--help` 或只看"装好了"会得出"工具就绪"的错误结论；真跑 `--timed` 才暴露 `failed to start trace session: access denied`（本机 `ADMIN=no`，且不在 Performance Log Users 组） | 任何"工具可用"的结论必须由**一次成功的采集会话**证明；失败时必须**捕获该报错原文并落成 `blocked` 记录**（`blockedReason="permission"`），不许写成"工具缺失"，更不许写成"测了没差" |
| **R5** | **"假节拍"——采集看起来在跑，节拍其实没钉住。** 两种表现：(a) GPU Timestamp Query 读不出（`stampFail` 高而 `disFail=freqZero=disjoint=0`，`h0=S_OK / h1=S_FALSE`）；(b) 读数"很漂亮"但其实是空转值（`CPU_FRAME_MS p50` 落在 **0.15~0.34ms** 级而不是 6ms 级） | 主理人实测：紧凑循环 **`GPU_VALID=1 (1%)`**；ping-pong **55%**；三组轮转 **54%**；加 `Sleep(1)` 只回到 55%；**`SyncInterval=1` + Waitable → 99%、`stampFail=0`**。<br>**关键更正（E14b）**：`SyncInterval=0` 时**照样能调到 waitable 并拿到 `OBJECT_0`** ⇒「能调到 waitable」不构成节拍证据（CAL-4 与 CAL-5 代码完全相同，仅 `SyncInterval` 0→1，p50 从 0.1786 → 6.0596） | ① 节拍成立需**两个条件同时满足**：**`SyncInterval` 必须为 1**（`Present1(1,…)`）**且** 必须用 `WaitForSingleObjectEx(frameLatencyWaitable)` 推进，**缺一即假节拍**；② 每条样本带 `gpuValid`，报告只统计 `gpuValid=1` 并明示有效率；③ **有效率 < 90% → 该次采集作废**（E14 实测 99%、90% 留余量；不许要求 100%，不许把无效样本当 0 或静默跳过）；④ **节拍自检**：`p50` 必须落在刷新周期 ±5% 内（§3.1 D2），落在 0.3ms 级即判假节拍、采集作废；⑤ 负控 **NC6**：改回紧凑循环 → 有效率跌到接近 0；**NC7**：`SyncInterval` 改回 0 → `p50` 必须从 6.06ms 级掉到 0.2ms 级，节拍自检必须变红 |

> **判据元规则（与 §3.2 的 blocked 三锁并列，写进纪律）**：任何"通路可用"的结论**不许**由「退出码 0 / 无异常 / 无报错 / 进程存活」推导出来，只能由"**具体字段非空 + 具体 HRESULT 为 0 + 两个计数相等**"推导。R1/R2/R3 的共同特征是"程序运行得很健康"，R4 是"工具看起来就绪"，R5 是"数据看起来齐了"（100 帧全跑完，但 GPU 一帧都还没画）——**四类都是"绿得毫无破绽"的假绿**——这是本次 Spike 最容易出**假绿**的地方，比数值造假更隐蔽，因为它不涉及编数字。

## 3. 裁决口径（本次 PRD 的核心，四张表）

### 3.0 三类标签，互斥且不可互相替代

采集与报告只允许出现三种状态：`pass` / `fail` / `blocked`。

- `blocked` **既不是通过也不是不通过**，它表示"本机没有能力观测"。
- 任何把 `blocked` 写成 `pass` 的报告 = 无效报告；任何把 `blocked` 写成 `fail` 的报告 = 同样无效（后者会造成"用环境缺陷否决一条通路"的冤判）。
- 三态由 schema 强制：`status` 字段是枚举，`blocked` 项**必须**带 `blockedReason` 与 `missingCapability` 两个非空字段（前者取 E3/E4/E5 之一，后者写缺的工具/硬件名）。缺这两个字段的 `blocked` 记录，校验器直接判为非法记录。

### 3.2 表 B：blocked-by-environment 清单（含 B1a 的降级可测口径）

> **先看这条拆分**：B1 原为一整条「显示延迟」，现按 E12 拆成 **B1a（`MsGPUBusy`，可降级测量、移出 blocked）** 与 **B1b（`DisplayLatency`，仍 blocked）**。
> 拆分理由：两者**观测手段不同、可得性不同、结论强度也不同**。合并成一条会造成两种错误——要么因为「显示延迟测不到」连带放弃本可测的 GPU 耗时，要么因为「GPU 耗时测到了」连带把显示延迟写成通过。
> **权重不受影响**：B1a/B1b 都**不占权重**（它们是 C2/C6 红线的观测手段，不是独立计分维），占权重的仍是 B2 10 + B3 10 = 20，覆盖率仍 **80%**。

**B 类的三条硬锁（全项目最容易被做假的地方，写成硬需求）**

1. **数据锁**：`status` 枚举里没有第四个值，`blocked` 只能由"缺能力"产生；采集器**不得**为 B1/B2/B3 生成任何数值字段（`value`/`p50`/`p95` 一律 `null`）。
2. **计分锁**：blocked 维度的权重（**B2 异 DPI 10 + B3 IME 10 = 20**，见 §4.0；B1 是观测手段缺失、不占权重）**不从分母里剔除、也不摊给 A 类**。裁决覆盖率单独作为指标上报，永远显示"80/100"，**不归一化到 100**。把 blocked 的权重摊给 A 类，会造出"看起来覆盖 100%"的假象——这是本次 Spike 最需要防的造假路径。
   **追加硬约束（主理人下发）：不得为了"凑齐五维"给 IME 造任何形式的合成得分。** 不接受"中性分""按 50% 估算""给个 0.5 当保底"。宁可**三维计分 + 三项 blocked 单列**，也不接受"多一维假分"。
3. **声明锁**：裁决报告必须逐字包含下面这句话，缺字即视为**无效裁决**（可由任务 #6 写成一条字符串精确匹配的 check）：

   > **「在 B 类 blocked 维度（DisplayLatency / 异 DPI 双屏连续拖拽 / 真实中文 IME 候选框定位）上，本机无法区分两条通路，因此本裁决仅基于 A 类维度。」**

   **并且**：报告 §B 必须单独出现一行「**IME 维度两通路均 blocked，裁决不依据该维度**」，与上面那句并存（前者是笼统声明，后者是逐维声明，缺任一即无效）。

### 3.3 表 C：绝对红线 → 本机可测的等价/替代指标 → 支持什么、不支持什么

源方案的红线是给"PresentMon + 120Hz + 异 DPI 双屏 + 真实 IME"这个环境写的。本机只有其中一部分，且**每一条的具体数值都不一样**（PresentMon 无权限、主屏 165Hz、只有一块屏、IME 无法驱动），因此每条红线都必须重述成**本机能测的等价物**，并**明写它不支持的结论**。

|---|---|---|---|---|

> **C 表的元规则**：任何在报告里出现的数字，都必须能指回本表某一行 + 某个采集文件 + 某条可复现命令。指不回去的数字一律删除。**"通常""一般""大概""约"这些词在本项目文档里禁止出现**（这是纪律，不是修辞偏好：模糊量词是编造数据的第一个入口）。

### 3.4 表 D：一票否决在 blocked 情况下如何执行

源方案说"某维度不达标即否决"。在本机有 **三项** blocked（B1b `DisplayLatency` / B2 异 DPI 双屏 / B3 真实 IME）的情况下，必须把否决权收窄到"有证据的维度"上，否则等于用环境缺陷判死刑。

| 规则 | 内容 |
|---|---|
| **D-1** | **一票否决只在 A 类维度上生效。** 触发 `fail` 的条件 = 采集文件存在 + 统计量越过 §3.1 判据 + 该统计量有**能把它变红的负控**。三者缺一，状态只能是 `blocked` 或 `untested`，**不许写成 `fail`** |
| **D-2** | **B 类（blocked）不触发否决，也永不用于"洗白"。** B1b/B2/B3 的 `blocked` 状态对裁决结果的贡献 = 0 分 + 覆盖率减 20 + 一句强制声明（§3.2 锁 3） |
| **D-3** | **A 类降级**：某 A 类维度在 **M2-b 采集窗口**内因工具/实现原因拿不到有效采集（含权限类失败，见 §2.1-R4） → 自动降级为 `blocked`（同样带 `blockedReason`），并按"降级即降权"处理：该维度权重不计入得分，覆盖率按维度权重递减，且裁决结论**降级为 `conditional`**（条件裁决），报告首页必须写明「本裁决缺少 N 个 A 类维度：<列表>」 |
| **D-4** | **B 类维度的失败代价后移**：B1/B2/B3 在 M3 真机复测中若不过 → **触发回滚**（切到另一条通路）。因此 M3 的 P0 任务必须包含「回滚路径与工作量估计」，M2 不要求做完，但要求**两条通路都保持可运行、可切换**（不许在 M2 就把另一条拆掉） |
| **D-5** | **`tie` 不是通过**。A 类维度记 `tie` 表示"在本机噪声内不可区分"，报告必须原样写 `tie`，不得写成"通过"或"接近通过" |
| **D-6** | **裁决级别只有三种**：`decided`（A 类全部出数、无 fail）、`conditional`（有 A 类维度降级）、`void`（A 类出现 fail 且两条通路都被否决，或采集文件不全）。`void` 时**禁止**进入 M3 业务代码开发，只能补测 |

### 3.5 `tie` 时的处置（PM 不越权拍板，但要把决策要素摆齐）

若 D1/D2 双双 `tie`，本次 Spike 的产出不是"选一条"，而是**一份带风险对价的决策清单**，交主理人在 M2 末决策会拍板。清单必须给出：

1. **被 blocked 维度的风险分布是不对称的**（这一条是本次分析的关键结论，必须进报告）：
   - 对 **B 通路**：IME 候选框定位（B3）是**结构性风险**——OSR 下 UI 没有真实 HWND 的 caret 语义，问题不是"调一调参数"，而是"要在原生侧重建一套 caret→候选框定位"。异 DPI 双屏（B2）对 B 是低风险（单链，只有一套 DPI 变换）。
   - 对 **A 通路**：双窗同步（B2 的邻域）是**主要风险**，但它在 A 类 D1 里已被实测覆盖到"同一合成帧内"的程度；IME（B3）对 A 是**零风险**（100% 原生输入法）。
2. **回滚成本不对称**：M3 复测不过时要切到另一条通路，A→B 与 B→A 的重建量不同，必须各自估一个人日数写进清单。
3. PM 建议（不具约束力）：`tie` 时倾向 **A**，理由是**剩余风险的可测性更好**——A 的未测风险（跨屏拖拽）在 M3 有明确可执行的复测手段，B 的未测风险（IME 候选框）在 M3 前没有任何缓解手段。但此建议不写进裁决结论，只写进"决策要素"。

## 4. 需求池（P0 / P1 / P2）

> **判据常量元规则**：任何判据常量（阈值、比例、周期数）必须同时写明 ①**来源**（实测 / 判据设计 / 外部标准）②**依据** ③**触发重标定条件**。三者缺任一，该常量**不得进实现**。
> 立这条规则的原因：本次自检发现四个判据常量里有两个是"裸数字"（无来源、无依据、无重标定条件）。它们不是负控期望值，所以"常量变而负控期望未变则门禁红"的校验抓不到它们——**一条抓不到的常量，改了只需过一次 diff，没人需要解释**。只补注那两个症状、不立规则，等于治好症状留着病根。
> **统计量分辨率元规则**：任何统计量在进入 Δ/N 比较前，必须声明其**分辨率**（量化步长），且**必须附分辨力证明**——**空对照（0 负载读数 ≈ 0）或负载扫描（大跨度负载下读数显著变化）二者之一**，无分辨力证明的绝对值类统计量**一律禁止作 Δ/N 输入**。同时**分辨率必须小于待分辨差异的量级**；分辨率 ≥ 待分辨差异 → 该统计量退出 Δ/N，改由其它统计量承担，**不得因"测得相等"而记 `tie`**。
> 立这条规则的原因：**假 tie 比假绿更隐蔽**。E15 证明 GPU 墙钟在 165Hz 满帧下分辨率为 1 个刷新周期（相对误差 ~100%），两条通路的真实差异 0.5ms 在物理上不可测，读数必然同为 `k=1`、`Δ=0`。若不作分辨率声明，报告会写出"两条通路 GPU 开销不可区分"——**那不是测出来的结论，是仪器精度不够造出来的结论**，而且它长得完全像正常结论，没有任何负控会报警。
>
> **同名不同物元规则（第五条）**：任何统计量**必须一名一物一区间**。R101 实测 `CPU_FRAME_MS` 这个名字同时指过两个物理量（累计时钟差分 = 整圈墙钟 vs. CPU 纯提交开销），差 80 倍，而两者都能给出"合理"读数。**改名不够**——必须**拆成物理可分的多个量并给出恒等式**（`SUBMIT+WAIT<=FRAME`）；恒等式不成立即说明采集窗口重叠，你读的量不是你以为的区间，该批数据作废。**凡「A/B 比值」形式的证据，必须写清 A 与 B 各自的物理定义与采集点**（反例：`rafFps/target` 在 60Hz 档巧合 100%，在 165Hz 档若 `setFrameRate` 未生效则比值仍可能 ≈100%）。
>
> **负载类型一致元规则（第六条）**：分辨力证明所用的**负载类型必须与被测量的物理维度一致**（CPU 时钟 → CPU 负载；GPU 时钟 → GPU 负载）。R101 实测：用 GPU `Clear` 扫描 1→640（80× 负载）去测 `SUBMIT_MS`，读数只从 0.0797 涨到 0.1064（**+33%**）——**这个「几乎不动」恰恰是仪器正确的表现**（Clear 是 GPU 命令）。**用错负载类型证明分辨力，比不证明更糟**：它会让人误以为「已证明」而放行一个恒真量。正确做法见 `COLLECTOR_CPU_BURN` 扫描：0→0.093 / 500k→1.72 / 2M→6.02 / 8M→23.5（跨两个数量级、三轮极差 <8%）。

### 4.0 权重与覆盖率（先定算法，再定需求）

源方案五维权重 **30 / 30 / 20 / 10 / 10**。本次落位：**D1 同步 30 · D2 开销 30 · D3 稳定 20 · B3 IME 10 · B2 异 DPI 10**（D4 确定性项为门槛，不占权重）。

> ⚠️ **待确认**：上表"权重↔维度"的绑定由 PM 按 d2 语义落位。若 d2 原文绑定不同，**替换绑定即可，§3 的四张表与 D-1~D-6 规则不受影响**（规则是权重无关的）。

- **加权得分**只在 A 类维度上计算：`score = Σ(维度得分 × 权重) / Σ(参与裁决的 A 类权重)`。
- **裁决覆盖率** = `Σ(参与裁决的 A 类权重) / 100`，本次理论上限 = **80%**。覆盖率**永远不归一化到 100%**，且必须与得分并列显示在同一行。
- **B1a（`MsGPUBusy` 降级测量）不新增维度、不改权重**：它由 **D2③ 的 D3D11 timestamp query** 承接，计分仍落在 D2（开销 30）内部。这一点必须写清楚，否则会出现"测到了就多一维、覆盖率凭空变 90%"的假象。
- 维度得分只取 `胜 = 1 / 平 = 0.5 / 负 = 0`（`fail` 直接触发 D-1，不进加权）。**不设连续分数**——连续分数会让"差一点"和"差很多"看起来一样，是另一种形式的模糊化。

### 4.1 相对裁决的可逆性规则（主理人下发，硬约束）

相对裁决**必须能反过来用**。只写"A 比 B 差 0.4ms，所以判 B"是无效论证，因为它没说这个差值是不是噪声。

| 规则 | 内容 |
|---|---|
| **R-1** | 任何一个"某通路在该维度更好"的结论，**必须同时给出两样东西**：① 两通路的统计量差值 Δ；② 该统计量的**噪声 N**（同通路重复 3 轮的同统计量极差/离散度，见 P1-2）。Δ 与 N 缺一，结论不成立 |
| **R-2** | `Δ <= N` → 判 **`tie`（两条通路在该维度不可区分）**，**不得**给任何一方加分。`Δ > N` 才允许判优劣 |
| **R-3** | 判优劣时**不按 Δ 的大小给分**。得分只有 1/0.5/0（§4.0）。Δ = 1.1N 与 Δ = 10N 得分相同——因为本机缺 `DisplayLatency`（E3），把"差多少"换算成"体验差多少"没有依据 |
| **R-4** | 噪声 N 必须来自**本机、同参数、同采集器版本**的重复轮次。**「同参数」= 同负载 + 同帧数 + 同采集节拍**（同一 Waitable 推进方式、同一目标刷新率档，见 R5）——**采集节拍不同，噪声本身就是假的，Δ/N 比较全部失效**。不许用文献值、不许用别的机器、不许用估算。**噪声 N 的采集是 P0 门槛项（`P0-13`），不是可选增强**。拿不到 N 时不是"记 `tie` 然后继续交付"，而是「**该维度无法裁决，M2-c 不能出终稿**」——前者会让报告带着一堆 `tie` 交付，后者会逼着去把 N 测出来 |

> 这条规则的意义：**它是"相对裁决"从"看起来科学"变成"真的科学"的分界线。** 没有 N，Δ 就是无法解释的数；有了 N，Δ 才有"可区分/不可区分"的语义。

#### P0-3 的双档三态判定（主理人下发，硬约束）

双档必须**分角色**，否则会变成一条新的假绿通道（"挑一档过就算过"）。

| 档位 | 角色 | 它回答的问题 | 失败时的影响 |
|---|---|---|---|
| **60Hz 档** | **基线档** | 「通路 B 的实现本身是否成立」——能否**持续**吃下 Chromium 纹理 | 不过 → **`P0-3 = FAIL`**（这是唯一真失败：实现不成立） |
| **165Hz 档** | **能力档** | 「这条通路在本机真实节拍（E4）下是否还有余量」 | 不过 → **不判失败**，只是"高刷余量未证出" |

| 组合 | `P0-3` 状态 | 裁决含义 |
|---|---|---|
| 60Hz 过 + 165Hz 过 | **`PASS`** | 实现成立且有高频余量 |
| 60Hz 过 + 165Hz 不过 | **`PASS_BASELINE_ONLY`** | **不算失败**。但必须在裁决报告里作为一条**显式的「高频余量不足」结论**出现，且**不得用它去否定通路 B 的可行性** |
| 60Hz 不过 | **`FAIL`** | 实现不成立，进入 D-1 否决流程 |

**为什么必须这么分**：若写成"两档都过才算通过"，165Hz 不过会让整条通路被判死；而实际上我们只是**没证出高刷余量**——那是**性能问题**，不是**可行性问题**。两者在 M2 的裁决权重完全不同：**可行性归 M2-a 门槛（过不了就没有这条通路），性能归 M2-b/M2-c 计分（差多少可以量化比较）**。混在一起会导致"用性能不达标否定一条可行通路"，这是本项目最容易犯的误判。

**落盘硬要求（防"只留结论、抹掉数据"）**：
1. 165Hz 档结果**必须原样落盘**，含 **`rafFps` / `targetFps` / `rafFpsDivTargetFps` 三项原始值**；
2. **不许只写「未达标」**，也不许把实际比值抹掉只留结论——**这个比值是 M3 决定「要不要给原生侧加 vsync 节流」的唯一依据**，抹掉了就白测；
3. 两档各自的 `env.json` 必须带 `采集档（165Hz | 60Hz）`（P0-1 已列），**不许两档共用一个 env 文件**；
4. `PASS_BASELINE_ONLY` 在报告里必须有独立的统计行，**不计入通过率、也不计入失败数**（同 §3.2 blocked 的处理手法：既不洗白也不判死）。

1. **`native/build/` 整个目录不入库** ⇒ 任何放在其下的 addon 源码、`binding.gyp`、构建脚本、骨架 js **在新 clone 里都不存在**，而 §2.2 C-3 要求"清空 build 目录能干净重建"——两者一撞就是"**重建无源**"。故这些**一律迁到 `native/spike-glass/` 下的 `addon/` 目录，构建脚本放仓根**（均 NOT-IGNORED）。
2. **`build/` 目录的 `.gitignore` 否定规则无效**：实测在 `.gitignore` 里加 `!native/spike-glass/build/*.bat` 后 `git check-ignore` **仍报 ignored**。只要目录层级被一条规则命中，其子文件永远进不来。⇒ **"加白名单解决"这条路不存在，不许写进任何任务卡**。
